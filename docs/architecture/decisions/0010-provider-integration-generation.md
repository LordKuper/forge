# ADR 0010: Provider integration generation

- Status: Accepted
- Date: 2026-08-17
- Contract version: 1.0.0

## Context

Stage 9 (P9.9-P9.16) needs to generate the native Claude Code and Codex
integration views `docs/architecture/overview.md`'s "Agent integration and
instance identity" section already commits to: "The `.forge/` compiler
generates Claude Code and Codex skill/plugin views from one canonical
integration source. Outputs contain source hashes, ownership markers, minimum
Forge/protocol versions, the built-in workflow invariants including the
implementation-first testing order, and no human-only authority... Generation
and optional installation are idempotent and never overwrite unknown
user-owned files." ADR 0005 adds one more constraint: "duplicate installations
are detected rather than left ambiguous."

This item is the *generation engine* only — pure computation from `.forge/`
content to in-memory artifacts. Writing those artifacts into each vendor's
real config location, detecting an existing installation, and removal are
P9.17-P9.24's separate concern (`capabilities.json`'s `integration.skill`
contract: `forge integration skill <generate|install|remove>`). This ADR does
not touch the filesystem outside `.forge/`.

ADR 0009 already produces validated `ForgeDocument`s from `.forge/rules/` and
`.forge/knowledge/`. ADR 0008 already established the pattern this generator
must follow for vendor-specific knowledge: the core knows nothing about
concrete providers; each vendor's own adapter project owns everything specific
to that vendor.

## Decisions

### One canonical source, generated once

`Forge.Compiler.IntegrationSourceCompiler` compiles a `ForgeDocumentSet` (ADR
0009) plus the project's artifact-language policy into one
`CanonicalIntegrationSource`: a single merged Markdown body (a localized
"generated by Forge, do not edit" preamble, the built-in
implementation-first-testing-order invariant, then every rule document, then
every knowledge document, each ordered by `RelativePath` for determinism) and
its metadata. This step knows nothing about Claude Code or Codex — it is
provider-agnostic by construction, matching ADR 0008's "the core knows only
[the neutral contract]" precedent extended to generation.

### Audience, language, and the capability gate

The generated body is `agent_facing` per overview.md's audience model: its
language comes from the project's `artifacts.language.agent_facing` policy,
resolved through the same shared `ILocalizationCatalog` every other surface
uses (one catalog, not a parallel one). Before generating,
`IntegrationSourceCompiler` checks `catalog.SupportedCultures` for that
language and refuses to generate (a typed `LanguageUnsupported` diagnostic,
never an exception) if it is missing — overview.md: "Missing artifact-language
capability blocks generation; it never silently falls back." The rules'/
knowledge documents' own Markdown bodies are admitted verbatim regardless of
this language (ADR 0009: authored content is never retranslated); only the
fixed boilerplate preamble and testing-invariant text are localized.

### Source digest and the ownership marker

The merged body is hashed (`sha256:` + lowercase hex, matching every other
digest in the codebase, e.g. `SprintOrchestrator.ArtifactPolicySnapshotHash`)
*before* any marker is added, so the digest is a pure function of canonical
`.forge/` content and resolved language — never of the generator's own
version or a timestamp, which would break reproducibility (identical
`.forge/` content and policy must always produce an identical digest). The
digest is then embedded in a single-line ownership-marker comment prepended to
the body:

```
<!-- Generated by Forge. Do not edit directly — edit .forge/rules/ or
     .forge/knowledge/ instead. source_digest=sha256:... generator_version=...
     schema_version=1.0.0 -->
```

`CanonicalIntegrationSource.SourceDigest` is this same value, exposed
separately from `Content` so a caller can compare it against a previously
recorded digest without re-parsing the marker out of file text — this
comparison *is* drift detection: unequal digests mean `.forge/` content or
resolved policy changed since the last generation; equal digests mean
regenerating would be a no-op. No separate drift-detection algorithm exists;
content-addressing already gives an exact, reproducible answer. Detecting
whether an *installed* file was hand-edited since Forge last wrote it (a
different question — comparing the marker's embedded digest against a fresh
recomputation) is P9.17-P9.24's concern, once there is an installed file to
compare against.

### One adapter interface per vendor, same pattern as `ILlmProvider`

```csharp
public interface IProviderIntegrationGenerator
{
    ProviderId ProviderId { get; }
    GeneratedArtifact Generate(CanonicalIntegrationSource source);
}
```

declared in `Forge.Providers` (`ProviderContracts.cs`) alongside
`ILlmProvider`/`IProviderReleaseSource`, and implemented once per vendor in
that vendor's own adapter project — `ClaudeIntegrationGenerator` in
`Forge.Providers.Claude.Windows`, `CodexIntegrationGenerator` in
`Forge.Providers.Codex.Windows` — registered through the same
`AddClaudeProvider()`/`AddCodexProvider()` composition roots ADR 0008 already
uses. The core (and `Forge.Compiler`) never names a vendor file format;
`IntegrationGenerationService` (`Forge.Application`) only ever calls the
generator whose `ProviderId` is in the project's enabled-provider set,
mirroring how disabled providers are never probed (ADR 0008).

Each vendor's `Generate` method owns exactly one fact the core must not know:
its well-known root-level instructions file.

- **Codex** reads `AGENTS.md` at the project root (the same convention this
  repository's own `AGENTS.md` uses). `CodexIntegrationGenerator` writes the
  full `CanonicalIntegrationSource.Content` there verbatim.
- **Claude Code** reads `CLAUDE.md` at the project root and supports a
  `@<path>` import directive — this repository's own `CLAUDE.md` already
  uses `@AGENTS.md` for exactly this purpose. `ClaudeIntegrationGenerator`
  writes a thin `CLAUDE.md` containing its own ownership marker plus
  `@AGENTS.md`, rather than duplicating the full body, so the two vendor
  files can never diverge in content — only Codex's file carries the full
  text, Claude's file always points at it.

A JSON/frontmatter-based "skill" or "plugin" package format was considered
and rejected for the MVP: neither vendor's current packaging schema is pinned
by any existing Forge contract, and inventing one on assumption risks
shipping a wrong, unverifiable format. The root-level instructions file is a
stable, well-documented mechanism for both vendors today; a richer package
format can be added as an additive minor contract change once one is
actually needed and its shape is confirmed.

`ClaudeIntegrationGenerator.Generate`/`CodexIntegrationGenerator.Generate`
themselves contain no OS-specific call — the vendor-file-name-and-shape
policy they encode would run identically on any OS. They still live in
`Forge.Providers.Claude.Windows`/`Forge.Providers.Codex.Windows` rather than
a portable location, matching where `ClaudeReleaseSource`/`CodexReleaseSource`
(also largely OS-agnostic) already live and where Stage 8's own ADR 0007
adapter-boundary audit already accepted them. ADR 0008 frames this
placement as vendor ownership, not OS-call translation: "One `ILlmProvider`
represents one complete integration"; each adapter project "exclusively
owns its vendor's paths, scripts, commands, authentication, environment, and
output normalization." A generated file's name and shape is exactly that
kind of vendor-owned knowledge. Splitting it into a third, portable
"provider-neutral-but-vendor-specific" location ahead of an actual
non-Windows provider adapter would add structure nothing consumes yet
(ADR 0009's own bias against building unused structure). Extraction remains
straightforward — pure string templating with no adapter-local state — if
and when a non-Windows provider adapter makes it worth doing.

### Generated-artifact metadata is a versioned contract

`docs/contracts/v1/schemas/generated-artifact.schema.json` (Draft 2020-12)
describes one `GeneratedArtifact`'s metadata — `provider_id`, `relative_path`,
`media_type`, `audience`, `language`, `source_digest`, `policy_snapshot_hash`,
`generator_version` — cloning `handoff.schema.json`'s existing `$defs.artifact`
shape (already `digest`/`media_type`/`audience`/`policy_snapshot_hash`/
`generator_version`, with the same audience/language conditional) rather than
inventing a new one, plus `provider_id`/`relative_path` this context needs
that a workflow handoff does not. `IntegrationGenerationService` validates
every artifact it produces against this schema before returning it — a
defense against a future adapter bug shipping a metadata shape the schema
would have caught, at negligible cost given the validator is already wired for
ADR 0009's schema.

## Consequences

Generation is a pure, side-effect-free library capability with no CLI command
yet — the same incremental layering ADR 0009 established: parse first, wire
into commands later. Reproducibility follows directly from content-addressing
the merged body; no separate reproducibility test infrastructure is needed
beyond asserting equal input produces an equal digest. Extending to a third
vendor means one new adapter project implementing `IProviderIntegrationGenerator`
and one new composition-root registration — the core, `Forge.Compiler`, and
this ADR's schema are unaffected.

| Action | Recovery |
|---|---|
| generate an integration source | pure computation; a language-capability failure returns a typed diagnostic and produces nothing |
| generate a provider artifact | a schema-validation failure on the produced metadata is a typed error; other providers' artifacts are unaffected |
