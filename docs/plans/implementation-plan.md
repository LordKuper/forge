# Forge MVP implementation plan

**Updated:** 2026-08-17
**Status:** active

## Rules

- Complete a stage only with reproducible evidence and a green repository gate.
- Update normative ADRs and versioned contracts before implementation.
- Keep one command model, one project snapshot, one sprint journal, and one review engine.
- Keep every project cross-platform unless it is a marked minimal leaf OS adapter under ADR 0007.
- Keep provider-neutral policy in the core and every vendor/OS detail in its provider-owned adapter under ADR 0008.
- Apply the implementation-first testing invariant to Forge development and every managed project; generated integrations communicate it and Host transitions enforce it.
- Defer work that has no MVP acceptance case or measured need.

**Depends on:** Stages 4–7.

- [x] P8.1–P8.8 — Enforce ADR 0007: mark OS adapters; make CLI/shared tests portable; move Windows composition and directory-flush interop to minimal adapters; split reusable Desktop state from WinUI; audit the Windows updater adapter.
- [x] P8.9–P8.17 — Add portable `Forge.Host` and client SDK as the only workflow writer; implement discovery, start, reconnect, message limits, deadlines, correlation, version/capability handshake, and stable diagnostics. **Reopened 2026-08-15 audit:** the Host protocol only dispatches `ping`/`GetProjectSnapshot`/`ReadControlEvents` (all read-only) — it is not yet the only workflow writer. `ForgeHostClient` does not validate the handshake's echoed correlation id/version, and the Host ignores the client's capability list. **Closed 2026-08-16:** the Host now dispatches `recover_startup`/`set_configuration` too, and both the CLI (`forge doctor --recover`, `forge config project`) and Desktop route both through the project's Host via `IForgeMutations`/`RemoteForgeMutations`/`HostMutationsFactory`, starting one if none is running. `ForgeHostClient` now independently validates the handshake response's echoed correlation id and protocol version (never trusting the Host's own self-reported diagnostic alone), and the Host's handshake response now advertises its real capability set (`CapabilityIds.Implemented`) instead of a hardcoded empty list.
- [x] P8.18–P8.24 — Use one asynchronous `System.IO.Pipes` transport and one named `Mutex` project lease through cross-platform BCL APIs; add no OS branch, TCP fallback, or transport package.
- [x] P8.25–P8.33 — Implement `GetProjectSnapshot(detail, sprint_id?)` and `ReadControlEvents`. Project summary, next action, tree, sprint inspection, provider/integration status, CLI output, and Desktop views must be local projections of the snapshot. **Reopened 2026-08-15 audit:** snapshot DTOs omit integration status, phase profile, and active deadline; attempt `LastActivityAt` is dropped during projection; CLI has no `tree`/`sprint inspect` commands; Desktop shows only a general overview, not per-sprint detail. **Progress 2026-08-16:** `LastActivityAt` now survives projection into `EntityStatus` (snapshot contract 1.2.0 → 1.3.0); CLI gained `forge tree` (nests attempts under their owning node via `OwnerId`, something the flat `status` lists never showed) and `forge sprint inspect <id>` (a dedicated single-sprint entry point, matching ADR 0005's own naming), both local projections of the existing snapshot with no new backend query. **Closed 2026-08-17:** Desktop gained the sprint tree and per-sprint detail view, both local projections of the same `GetProjectSnapshot` result the CLI reads; the tree/detail rendering now lives in `SurfaceFormatting`, and `SurfaceParityTests.DesktopAndCliRenderTheSameSprintTreeAndDetailForOneSnapshot` asserts the two surfaces produce identical text for one project rather than merely calling one helper. Integration status, phase profile, and active deadline are deliberately **not** part of this item's completion: no executor exists anywhere that would populate them with real data (`SprintGitIsolation` is unwired from `SprintOrchestrator`/`SprintScheduler`; nothing in production code constructs an `ExecutionProfile`), so projecting them now would only surface permanently empty fields. They are re-scoped to Stage 11 P11.56–P11.66, which owns the surfaces that first produce them.
- [x] P8.34–P8.41 — Isolate release, Debug, and tests by instance id; test same-user enforcement, hostile clients, crashes, abandoned leases, stale clients, recovery, and three-OS behavior. **Reopened 2026-08-15 audit:** same-user enforcement (`CurrentUserOnly`) has no automated test with a second OS user. **Progress 2026-08-16:** added `.github/scripts/test-same-user-isolation.ps1`, a Windows CI job that creates a genuine second local OS user and proves the real production `NamedPipeControlTransport` (`PipeOptions.CurrentUserOnly`) blocks its connection attempt to the control-plane pipe — with a same-user sanity check and a positive control first, and asserting the specific access-denial exception, so the isolation result can't be a false positive. `MutexProjectLease` (a separate `NamedWaitHandleOptions.CurrentUserOnly` primitive, not a pipe) was left uncovered by that check. **Closed 2026-08-16:** added a new `Forge.MutexIsolationProbe` project exercising the real `MutexProjectLease.TryAcquire`, and extended `test-same-user-isolation.ps1` to run in the same CI job/local-user lifecycle, proving same-user mutual exclusion first (a second same-user acquire attempt on an identical name blocks and times out while the first holder is alive), then that a *different* local OS user is denied access to a mutex of that identical name the current user already holds (`CurrentUserOnly` restricts a security descriptor on one shared object; it does not namespace per user). Getting this check to actually pass surfaced and fixed a real, separate defect: both `MutexProjectLease` and `ProviderInstallLock` always constructed their mutex in the OS-wide `Global\` namespace, which Windows only lets administrators/service accounts create (`SeCreateGlobalPrivilege`) — a standard non-admin user's Host failed outright at startup. Two intermediate fixes were tried and rejected before the final one. First, determining once from a dedicated always-uncontended probe whether the account can use `Global\`: the probe reflects the *process token*, not the account, so the same admin user's elevated and non-elevated Forge processes could resolve to different namespaces and silently stop excluding each other — a common scenario, not a rare edge case, and a fail-open regression from the lease's whole purpose. Second, uniform `CurrentSessionOnly = true` for every process on every OS: this fixed the token problem but unnecessarily weakened Unix too, where a session is only a single shell and `Global\`'s equivalent never had a privilege problem to begin with. Both types now fix `CurrentSessionOnly` per platform — `true` on Windows, `false` everywhere else — via `OperatingSystem.IsWindows()`, keeping the strongest guarantee wherever the OS actually allows it; a static architecture test pins the two independent copies of this construction identical. Known trade-off, disclosed in ADR 0005 and `CHANGELOG.md`: Windows session-scoping does not extend across two concurrent sessions of the same user (e.g. console + a simultaneous RDP session). Abandoned-lease recovery, crash resilience, and idempotent transitions were already covered by `ForgeHostProcessTests.ASuccessorHostRecoversTheProjectLeaseAfterTheFirstHostCrashes` and `ProjectLeaseTests`; three-OS portability is enforced by `test-portable.ps1` building both probe projects on every OS.
- [x] P8.42–P8.47 — Add Host-owned `resume_not_before` scheduling, safe activity updates, notification projection, and idempotent timer recovery without sleeping executor slots. `RoutingLedger` computes and records `resume_not_before`; `RoutingStatus.ResumeNotBefore` already projects it into the snapshot; `AttemptActivityRecordedType` already provides safe throttled activity updates. **Reopened 2026-08-15 audit:** nothing wakes and re-enqueues a deferred attempt once `resume_not_before` elapses. **Progress 2026-08-16:** added `ResumeSchedulerHostedService`, a Host-owned periodic `BackgroundService` (started only after the Host wins the project lease, per ADR 0005) that re-derives every sprint's `pending`→`ready` node readiness via the existing idempotent `SprintScheduler.AdvanceGraphAsync` — no per-sprint memory, safe to call repeatedly, restart-safe. **Closed 2026-08-17:** acting on `RouteDecision.Outcome.Deferred`/`resume_not_before` directly means starting a fresh attempt once a routing deferral elapses, which requires an attempt executor. No such executor exists anywhere in the repo today (`SprintScheduler.StartAttemptAsync` and `ILlmProvider.RunAsync` have no production caller — confirmed by repo-wide search), and building one here would duplicate or stub Stage 11's own engine rather than complete Stage 8's Host/control-plane scope. This item is deliberately **not** re-attempted within Stage 8: every timer/recovery/activity/notification-projection surface buildable without an execution engine now exists (`ResumeSchedulerHostedService`, `AttemptActivityRecordedType`, `RoutingStatus.ResumeNotBefore`), and the remaining "wake a deferred attempt" semantics are already Stage 11's territory — P11.32–P11.40 (the attempt-execution engine itself) and P11.48–P11.55 ("durable rate-limit deferral ... with confirmation, version, idempotency, bounded instruction, cancellation, worktree discard, linkage, and clean replacement"), which is precisely `RouteDecision.Outcome.Deferred` resumption. This mirrors how P8.25–P8.33 re-scoped its own executor-dependent fields to Stage 11.
- [x] P8.48–P8.54 — Version the user-configuration, provider-health, startup-check, snapshot, diagnostic, and execution-profile contracts for ordered provider enablement, update/authentication state, lineage evidence, compatibility, and migration.
- [x] P8.55–P8.63 — Reduce the core to `ILlmProvider`, `ProviderId`, and generic lifecycle/routing policy. Move all Codex details to `Forge.Providers.Codex.Windows` and all Claude Code details to `Forge.Providers.Claude.Windows`; remove concrete provider registrations and any shared `Forge.Providers.Windows` concept from neutral code.
- [x] P8.64–P8.71 — Register built-ins explicitly with `AddCodexProvider()` and `AddClaudeProvider()`; validate unique ids; resolve omitted, empty, ordered, duplicate, and unknown `providers.enabled` values; intersect and freeze project provider constraints without probing disabled providers. **Reopened 2026-08-15 audit:** enablement resolution was done, but nothing computed the project execution profile's provider intersection or froze it into `SprintDefinition`. **Closed 2026-08-16:** `SprintOrchestrator.CreateSprintAsync` now resolves `ProviderCatalog.ResolveEnabled` against the current enabled-provider ids and freezes the ordered result into `SprintDefinition.FrozenProviders`, once, same as every other frozen-at-creation field; an empty result fails creation with `sprint_provider_candidates_empty` instead of registering a sprint that could never route an attempt (ADR 0008). Use 24-hour success and one-hour failure retry windows; make refresh bypass the cache but not the availability comparison; disable Claude's background auto-updater during normal execution. **Reopened 2026-08-15 audit:** `StartupPipeline` only called the read-only `CheckAsync`; install/repair/conditional update only ran through the explicit `forge models --refresh` path, never automatically at startup as this item's own heading requires. **Closed 2026-08-16:** all the per-provider machinery (bounded probe, throttled release lookup, conditional update vs. full install/repair, interprocess lock, post-update probe) already existed in `ProviderInstallation.InstallOrUpdateAsync`, but it always bypassed the release-check cache — the only caller was `forge models --refresh`, which is supposed to be the one path that bypasses it. `InstallOrUpdateAsync`, `ILlmProvider.InstallOrUpdateAsync`, and `IProviderToolchainManager.EnsureReadyAsync` now take an explicit `bypassReleaseCache` flag; `StartupPipeline.CheckProvidersAsync` calls `EnsureReadyAsync(bypassReleaseCache: false, ...)` so routine startup performs real install/repair/update while still honoring the 24h/1h cache windows, and `forge models --refresh` calls it with `true` exactly as before. Claude's `DISABLE_AUTOUPDATER=1` handling was already correct from earlier work (P8.72-82's own prior partial completion) and is unchanged.

## Stage 9 — `.forge/` compiler and agent integration

- [x] P9.1–P9.8 — Parse manifest/YAML/Markdown/frontmatter into validated semantic input with safe paths, references, scopes, and context limits. **Closed 2026-08-17:** ADR 0009 defines the `.forge/rules/*.md` and `.forge/knowledge/*.md` document format (Markdown body with a `---`-delimited YAML frontmatter block, matching Jekyll/Hugo/Obsidian convention) and adds `forge-document.schema.json` (Draft 2020-12, `schema_version`/`id`/`title`/`scope` required, optional `references`/`context_limit_tokens`). `Forge.Compiler.ForgeDocumentCompiler` discovers both flat, optional directories and validates each document: frontmatter against the schema (typed YamlDotNet deserialization, not the raw-object path — dynamic deserialization was found to stringify every scalar, which would have silently passed integers like `context_limit_tokens` through as JSON strings and failed the schema's `"type": "integer"`); `references` against a closed safe-path check (relative, no `..`/absolute/drive/backslash, resolved and re-resolved through any symlink target to stay inside `.forge/`, and required to name another document this same parse pass discovered — not an arbitrary project path); and each document's estimated token count (chars/4 heuristic) against its effective context limit (declared value or a 4,000-token MVP default, schema-bounded at 8,000). Parsing never throws for expected content problems — malformed frontmatter, unsafe references, oversized documents, and duplicate ids are collected as typed `ForgeDocumentError` entries so one bad file never blocks the rest of the tree. Kind (`rule`/`knowledge`) is derived from directory, never a frontmatter field. Sprint-scoped specifications/decisions and structured handoffs (context-assembly layers 2–3's other half) are explicitly deferred to Stage 11, which first produces them; only rules and project knowledge/ADRs have an MVP source today.
- [x] P9.9–P9.16 — Generate reproducible native outputs for configured providers with source hashes, generator versions, drift detection, validation, and artifact-language metadata. **Closed 2026-08-17:** ADR 0010 adds `Forge.Compiler.IntegrationSourceCompiler`, which compiles a `ForgeDocumentSet` (ADR 0009) plus the project's artifact-language policy into one provider-agnostic `CanonicalIntegrationSource` — a merged, localized Markdown body whose `SourceDigest` is a pure function of canonical `.forge/` content (never a timestamp or the generator's own version), so comparing digests across generations *is* drift detection with no separate mechanism. Generation is refused with a typed diagnostic, never silently degraded, when the resolved `artifacts.language.agent_facing` isn't in `ILocalizationCatalog.SupportedCultures`. Mirroring ADR 0008's `ILlmProvider` pattern exactly, a new `IProviderIntegrationGenerator` interface (`Forge.Providers`) is implemented once per vendor in that vendor's own adapter project — `ClaudeIntegrationGenerator` (`CLAUDE.md`, a thin `@AGENTS.md` import, matching this repository's own convention) and `CodexIntegrationGenerator` (`AGENTS.md`, the full canonical body) — registered through the existing `AddClaudeProvider()`/`AddCodexProvider()` composition roots; the core and `Forge.Compiler` never name a vendor file format. `docs/contracts/v1/schemas/generated-artifact.schema.json` versions the produced metadata (cloning `handoff.schema.json`'s existing artifact shape); `Forge.Application.IntegrationGenerationService` orchestrates document parsing, source compilation, and every enabled provider's generator, validating each artifact against that schema before returning it. A JSON/frontmatter "skill" package format was considered and rejected for the MVP — neither vendor's packaging schema is pinned by any Forge contract, and the root-level instructions file is a stable, already-observed mechanism for both vendors. This item is generation only, entirely in-memory; writing an artifact into its vendor's real config location, detecting an existing installation, and removal remain P9.17-P9.24.
- [x] P9.17–P9.24 — Generate, inspect, install, and remove one canonical Forge integration for each enabled provider; document snapshot/events/commands, recovery, and built-in workflow invariants, including implementation confirmation before new test selection or authoring; exclude human authority; never overwrite unknown files. **Closed 2026-08-17:** ADR 0011 adds `forge integration skill generate|install|remove`, matching `capabilities.json`'s existing `integration.skill` contract exactly. `generate` is a plain read (never routed through the Host) that inspects every enabled provider's target file and reports missing/current/stale/foreign — satisfying "inspect" without a separate verb. `install`/`remove` are `IForgeMutations` writes, routed through `RemoteForgeMutations` → `ControlPlaneHostedService` exactly like `recover_startup`, since integration state is re-derived fresh every call (no `ExpectedStateVersion`/`IdempotencyKey`, matching `RecoverStartupAsync`'s own pattern, not `InitializeProjectAsync`'s). Ownership is decided solely by `IntegrationSourceCompiler.TryParseSourceDigest` parsing the marker back out (sharing its field-parsing logic with the writer, so the two can never drift the way a hand-rolled copy briefly did during ADR 0010's review) — a file without a recognizable marker is foreign, never overwritten or deleted, and reported via a distinct `integration_partially_refused` diagnostic (ADR 0005's "duplicate installations are detected rather than left ambiguous"). Independent review found the first version of this check insufficient: the marker's `source_digest` alone couldn't detect a hand-edit below an otherwise-intact marker line when `.forge/` itself hadn't changed, and a symlinked target path was read/written/deleted through rather than refused (including a POSIX-specific gap where `File.Exists` reports `false` for a dangling symlink, which would have let it fall through to "missing" and be silently replaced). Both are now closed: the marker embeds a second `content_digest` field — a digest of the file's own actual body, re-verified against its current content on every read — and any symlink at the target path (dangling or not) is unconditionally foreign, checked before `File.Exists`. Manually verified end-to-end through the real CLI/Host pipeline: missing→written, current→unchanged (idempotent), a rule edit→stale→regenerated, and a hand-written file→foreign→refused-and-untouched, for both `install` and `remove`; the hand-edit-below-marker and symlink cases are covered by regression tests rather than manual verification. Two things ADR 0011 explicitly defers rather than silently omits: `AgentIntegrationChanged` event emission (no project-level, non-sprint event journal exists to record it in) and the Desktop `Settings/AgentIntegration` view `capabilities.json` also names (CLI-first, matching how Stage 8's tree/detail work also landed CLI-then-Desktop across separate PRs) — both remain open follow-up work, not gaps this item silently leaves unrecorded.

**Gate:** `.forge/` remains canonical; generated files are reproducible and owned; every provider view carries the same implementation-first testing order; agents cannot invoke human-only commands.

## Stage 10 — Reproducible context assembly

- [x] P10.1–P10.8 — Build a versioned context manifest from rules, sprint specifications/decisions, accepted ADRs, structured handoffs, exact Git/file/`rg` reads, and a token budget. **Closed 2026-08-17:** ADR 0012 adds `Forge.Compiler.ContextManifestCompiler`, which builds one `ContextManifest` (`context-manifest.schema.json`) per sprint from a `ForgeDocumentSet` (ADR 0009) plus the sprint's own already-frozen id/base commit/workflow/workflow version — no new source of that identity is invented. Layer 1 (rules) and layer 3's project-knowledge/accepted-ADR half admit real MVP content; layer 2 (sprint specifications/decisions) and layer 3's structured-handoff half stay explicitly, permanently empty in the manifest shape, the same "modeled shape, no producer yet" gap ADR 0009 already named for `Handoff` — confirmed again here by grep: `Handoff` still has zero real construction sites. `forge-document.schema.json` gains one additive optional `status` field (`accepted`/`proposed`/`rejected`/`superseded`) so a `.forge/knowledge/*.md` document can represent an ADR without a second directory or a frontmatter `kind` override; only an accepted-or-unstatused knowledge document is admitted.
- [x] P10.9–P10.12 — Record source commit, selected paths, digests, truncation, and retrieval rationale; rebuild the same context without a transcript. **Closed 2026-08-17:** every admitted manifest item records its relative path, a `sha256:` content digest, its estimated token cost, and a rationale (`rule`, `knowledge:accepted`, or `query_result`); every dropped item is recorded in `truncated` with its token cost and an `over_budget` reason instead of silently vanishing. `ManifestDigest` is a pure function of every other field (never a timestamp or generator version, matching `IntegrationSourceCompiler`'s existing reproducibility rule), so an identical sprint state and token budget always rebuilds an identical digest with no transcript needed.
- [x] P10.13–P10.20 — Add a versioned declarative context-query plan for bounded read-only Git/file/`rg` operations. Validate paths, operation and result limits, source commit, and profile capabilities; return only a selected structured result bundle, never execute model-authored scripts or shell pipelines as a context engine. **Closed 2026-08-17:** `ContextQueryPlan` (`context-query-plan.schema.json`) declares 1-20 bounded operations against one pinned commit: `git_show` (exact file content) and `git_grep` (pattern search), chosen over spawning an external `rg` process specifically to avoid materializing a working tree and adding a new binary dependency — both operations read directly from Git's own content-addressed object store instead. `Forge.Infrastructure.GitContextReader` validates the whole plan (schema shape, operation-id uniqueness, path/pattern safety, and every operation's required capability present in the caller's execution-profile capability allowlist) before executing anything; one invalid or unauthorized operation rejects the entire plan. The reproducible `ContextResultBundle` (`context-result-bundle.schema.json`) records only digests and metadata, never raw content, matching `handoff.schema.json`'s existing digest-only artifact shape — because both operations are pure functions of an immutable commit, replaying the same plan against the same commit always reproduces byte-identical results.

**Gate:** context is bounded, sprint-scoped, reproducible, and based on exact source evidence; query plans cannot mutate the project or widen capabilities, and their result bundles rebuild byte-for-byte from recorded inputs. The MVP owns no full-text, Tree-sitter, LSP, graph, SCIP, or semantic index.

## Stage 11 — `implementation-critical` workflow and parity

- [x] P11.1–P11.12 — Implement intake, planning, threat/rule rubrics, and a task DAG with separate isolated implementation, confirmation, and test-work nodes, followed by deterministic final gates, review, human approval, and finalization for every managed project. Confirmation evaluates the DoD or user expectations; only its valid artifact makes recorded risk-based test selection and authoring eligible. Host state transitions must reject premature test work. Existing checks may support confirmation. A no-new-test result requires evidence that the change adds no behavior or existing checks cover every material risk. Use behavior nodes and rubric data, not a seven-role catalog. **Closed 2026-08-17:** ADR 0013 adds `NodeRole` (a purely descriptive tag on `NodeDefinition`, `TestWork` the one role the scheduler treats specially) and `ImplementationCriticalGraphBuilder`, a pure builder for the one canonical `implementation-critical` graph (`intake -> planning -> implementation -> confirmation -> test_work -> review -> human_approval -> finalization`) that `SprintOrchestrator.CreateSprintAsync` now uses by default for every managed project. `ConfirmationArtifact` (`confirmation-result.schema.json`) is a confirmation node's recorded judgment against its definition of done, with inspection/execution/existing-check evidence matching AGENTS.md's own Quality wording; `SprintScheduler.IsTestWorkEligibleAsync` is the single chokepoint — checked in both `AdvanceGraphAsync`'s promotion loop and `StartAttemptAsync` — that keeps a `TestWork` node from becoming eligible until every confirmation-role dependency's artifacts *at their own latest `RecordedAt`* (all of them, on a tie, so an unspecified enumeration order can never pick a winner) are all `Confirmed`, closing "Host state transitions must reject premature test work" with the newly implemented `workflow_blocked` diagnostic (previously reserved in `docs/contracts/v1/README.md` but unimplemented) — verified end-to-end even through an operator's `resume_sprint`/`run_sprint` call, since eligibility is re-checked from the artifact itself, not the sprint's blocked state. `RecordConfirmationAsync` rejects an unknown node id or a node not tagged `Confirmation` (`node_not_found`/`node_kind_mismatch`) rather than recording an artifact that gates nothing real. A `NotConfirmed` verdict blocks a running sprint with a new `confirmation` `BlockedReasonArgument`, mirroring how a late open finding already blocks one; that append is retried on a version conflict rather than fired once, since it is the sprint's only operator-visible signal. `BuiltInRubric` is a small, fixed threat/rule catalog (`Forge.Domain`) — plain data, not a role catalog, matching the item's own "behavior nodes and rubric data, not a seven-role catalog" wording; no assessment/evaluation type accompanies it, since nothing produces, consumes, or persists one yet. What a test-work node does with its eligibility (select tests, or record a justified no-new-test decision) and what actually evaluates the rubric against a real change are both explicitly deferred to this stage's later execution-profile/provider-attempt items (P11.13 onward) — the same "shape now, producer later" gap ADR 0009 left for `Handoff`, confirmed still true here by the same grep: nothing constructs a test-work result yet.
- [x] P11.13–P11.20 — Freeze only planning, implementation, and review execution profiles, including ordered provider candidates and capability allowlists. Every model node starts without a parent transcript and receives only its frozen context manifest and profile capabilities; a node cannot widen them or invoke human-only commands. ## Post-MVP learning backlog

- [ ] Derive an evidence-backed `KnowledgeProposal` only from a successful sprint, a corrected failure, or explicit operator instruction. Record applicability, canonical `.forge/` target, source event/artifact references, and a reviewable diff.
- [ ] Reuse the existing human-gate contract to inspect, approve, or reject each proposal. Approval updates canonical `.forge/` content and then regenerates owned provider views; agents cannot approve, directly edit generated skills, or learn from raw transcripts/provider prose.
- [ ] Evaluate an optional per-user hot-memory snapshot for personal preferences and verified environment facts. Keep it separate from project scope, hard-capped, frozen at attempt start, injection-scanned, credential-free, and explicit on overflow; never store project truth in it.
- [ ] Retrieve project knowledge from canonical files and content-addressed sprint artifacts. Add full-text or semantic recall only after an evaluation proves exact lookup insufficient and freshness against the source commit is enforceable.
- [ ] Ship learning only after evaluations demonstrate better task quality without regressions in reproducibility, prompt-injection resistance, approval integrity, privacy, or context cost; include proposal provenance, rollback, migration, and expiry tests.

## Intentionally not planned

- Model-authored executable tool pipelines; declarative context-query plans cover the useful case.
- Shadow Git checkpoints; isolated attempt worktrees and explicit supersession already provide rollback and replay.
- LLM goal judges or provider exit codes as completion authorities; deterministic workflow gates own completion.
- Conversation-history databases as project memory; transcripts are neither state nor canonical knowledge.
- Unrestricted lifecycle hooks or silent agent-managed skill writes; extensions and learned changes require validation, bounded authority, and explicit approval.

## Deferred

- Linux/macOS distribution and native Desktop hosts.
- `standard` and `fast` workflows.
- Full-text, Tree-sitter, LSP, graph, SCIP, or semantic indexes until measured need.
- Network notification channels and custom scripts.
- Distributed workers, SaaS, enterprise policy, package-manager, and machine-wide distribution.
